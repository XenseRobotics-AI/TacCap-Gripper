# 夹持控制重构方案：对齐 motorbridge 分层

状态：**已实施**。主机侧接触状态机在 SDK 0.2.0 删除（commit `5b8b3bf`），
0.2.1 补上闭合端有界前馈预压。方案里标「实测」的数字来自固件 1.1.6.20 / EL05 / 24V /
2026-09-13；**重构后的复测见 §1.2 末尾**（固件 1.2.5 / SDK 0.2.1 / 2026-09-22）。

---

## 1. 为什么要改

`ForcePositionController` 在主机侧跑了一套**接触判定状态机**：`Closing`/`Opening`
行进，靠速度+力矩判据识别堵转，连续 N 帧确认后切进 `HoldingForce`。围绕它衍生出
`arrival_band_rad`、effort 判据、`contact_samples`、`startup_guard_ms`、
`brake_distance_rad` 一整套边界条件。

三个问题，按分量排：

### 1.1 它重复了固件已经在做的事

MCU 侧已有 `task_canmotor_is_stalled()`（同样的速度+力矩判据）、限位保护、运动包络
（位置误差钳位 + I2t + 温度墙）、两级主机看门狗。项目早先已确定**读法 A：MCU 保留
实时控制与安全**。主机再做一套堵转判定，是把同一件事摊到两处——比放在任何一处都差：
两边的阈值、滤波、确认窗口各自演化，而真机上只有一个物理事件。

### 1.2 为了让状态机能判断，控制被做软了

行进段发的是 `{p, kp=0, kd, 0, v_ref}`——**没有位置项**的纯比例速度环，
`kd = grasp_torque / close_speed`。`kp=0` 是刻意的：有位置项就会产生力矩，堵转特征
就不干净了。

代价是实测抖动（10 轮、满 100Hz 回调采样）：

| 方向 | 相对速度纹波 σ | 峰峰 | 极限环频率 | 均速/命令 |
|---|---|---|---|---|
| 闭 | **37%** | 0.59 rad/s | 12–13 Hz | 77% |
| 开 | **24%** | 0.51 rad/s | 20 Hz | 94% |

四组对照（A `kd`0.70 / B `kd`1.40@v0.5 / C `kd`1.40@v0.25 / D `kd`2.00）证明
**纹波跟 `kd` 走、不跟速度走**（B≈C，两者都优于 A），排除机械共振。折算等效扰动
≈0.1 N·m（摩擦/齿槽量级），速度误差就是它除以 `kd`。

位置逆向帧 0/300——爪子从不倒退，是速度脉动不是振动。力矩领先速度 2 帧（20ms，
相关 +0.497），典型的滞后速度环。

#### 重构后复测（2026-09-22，固件 1.2.5 / SDK 0.2.1，10 轮，同样满 100Hz 采样）

`python/examples/control_ripple.py` 跑出来的，指标定义与上表一致：

| 控制器 | 方向 | 相对纹波 | 峰峰 | 均速/命令 | 逆向帧 |
|---|---|---|---|---|---|
| ForcePosition | 闭 | **11.4%** [10.4–11.6] | 0.269 | **98%** | 0/1468 |
| ForcePosition | 开 | **9.9%** [9.6–10.2] | 0.220 | **103%** | 0/1467 |
| Impedance | 闭 | **7.7%** [7.3–8.4] | 0.440 | — | 0/632 |
| Impedance | 开 | **8.5%** [7.8–8.8] | 0.464 | — | 0/653 |

对比重构前的闭合 37% / 张开 24%：**纹波降到约三分之一，而速度跟踪从 77% 升到 98%**。
§1.2 判定的成因（行进段 `kp=0` 的纯速度环，纹波跟 `kd` 走）因此被证实 —— 换成时间
基准斜坡 + 带位置项的命令之后，两个量同时变好，而这两者在原设计里是互相拉扯的。

三点说明，免得这张表被过度解读：

- **阻抗那两行的「均速/命令」没有意义**，留空。它的接近速度由 `peak/kd` 决定，不看
  `close_speed_radps`；实测均速是参考值的 2.5 倍，这也是它峰峰更大而相对纹波更小的
  原因 —— 分母不一样。
- **极限环频率没有进表。** 新测法是去均值后数过零（23.6 / 24.1 Hz），而上表那组
  12–13 / 20 Hz 的测法没有记录在案。数值不可比，列在一起只会误导。
- 逆向帧仍然是 0，结论不变：是速度脉动，不是振动。

### 1.3 分类问题本身不可靠

`HoldingForce` 与 `HoldingPosition` 的边界要靠 effort 判据
（`to_target >= grasp_torque / position_kp`）来分。这个阈值在默认参数下是 0.0175 rad，
而判据依赖的几何量在 Stage 0 之后已经变过。真机上反复测，得到过 0/10、1/3、3/5 三种
假阳性率——**其中两次是设备退化态污染的**（见 SLAVE_AUDIT.md），健康设备上是 0/10。
但这说明该判据的可测性很差：它区分的是「到位」与「被挡住」，而这两者在空爪场景下
物理上本就连续。

## 2. 0.35 N·m 这个默认值来路不正

```c
/* App/protocol/protocol_data.h:462 */
#define GRIPPER_AUTO_CAL_DEFAULT_CLOSE_TORQUE  0.35f
```

这是**自标定顶到机械停止点用的堵转力矩**（`task_canmotor.c:70`：「自标定用速度命令
顶到 close_stall_torque_nm 堵转、后退、回位、带载设零」）。
`ForcePositionConfig::grasp_torque_nm = 0.35f` 只是把这个数抄了过来，**没有作为夹持力
的论证**。

对照 EL05 官方规格：**连续堵转额定 1.1 N·m（可无限期）**，额定 1.8 N·m。0.35 只有
连续额定的 32%，而机构摩擦约 0.1 N·m——**扰动占了总控制权限的 29%**。

这直接解释了 §1.2 的抖动：D 组 grasp=1.0 时摩擦占比降到 10%，纹波实测降到 **14%**。

> **抖动不是控制结构缺陷，是权限约束。** 扰动占总权限三成时速度不可能平顺。

## 3. 目标架构

三层，对齐 motorbridge（`motor_vendors/robstride_mit/src/motor.rs` 的 vendor 层只有
`enable_drive` / `disable_drive` / `set_mode` / `command_mit(pos,vel,kp,kd,torque)` /
`command_position` / `command_velocity` / `read_parameter` / `query_status`——
**没有接触判定、没有状态机、没有夹持策略**）。

```
固件 (MCU)        实时控制 / 限位 / 包络 / 看门狗 / 自标定      ← 不动，读法 A 的前提
  ↑
SDK Motor         薄命令层：submit_* / enable / disable / 查询   ← 对齐 motorbridge
  ↑
SDK 夹持层        一条有界力矩阻抗命令 + guard + 观测量          ← 删掉 FSM
```

### 3.1 夹持 = 一条有界力矩的阻抗命令

```
command(target = 目标位置, kp, kd, torque_limit = 夹持力)
```

- **自由行程**：所需力矩 ≈ 摩擦，远低于上限，不受限
- **接触**：位置误差增大 → 力矩升到上限**自动饱和** → 这就是夹持
- **全程一条控制律，没有模式切换**

接触是隐式的。力控本来就不需要显式识别接触事件。

### 3.2 `ImpedanceController` 已经是目标形态

这一点值得单独说：仓库里更新的 `ImpedanceController` 已经基本对了——

- `stalled()` / `torque_capped()` 是**观测量**（bool getter）
- `stall_clamped_` 纯粹是标志，**从不改变控制律**
- 只有**一处**模式切换（`TorqueCapped` → 纯前馈保持），且是**持续力矩保护**驱动的
  安全动作，不是物理事件分类

所以本方案不是引入新范式，而是**把 `ForcePositionController` 拉到 `ImpedanceController`
已经站的位置**。

## 4. 现有逻辑的去向

| 现有 | 去向 | 理由 |
|---|---|---|
| `Closing` / `Opening` 状态 | **删** | 方向由目标隐含 |
| `HoldingForce` / `HoldingPosition` 状态 | **降级为观测量** | 见 §5 |
| `contact_candidate_()` 速度+力矩堵转判据 | **删** | 重复固件 `task_canmotor_is_stalled()` |
| `contact_samples_` / `stall_hold_ms` | **删** | 随判据一起 |
| `startup_guard_ms` | **删** | 只为躲开加速段的力矩尖峰，力矩上限本身已经管住 |
| `arrival_band_rad` | **删** | 到位是观测量（`\|误差\| ≤ ε`），不是状态 |
| effort 判据 `to_target >= grasp/kp` | **删** | 只为分类而存在 |
| `brake_distance_rad` + 刹车段 | **删** | 单一控制律无需分段 |
| 行进段 `kp=0` 速度阻尼 | **删** | §1.2 的抖动成因 |
| `position_hold_()` 的误差钳位 | **保留** | 这正是「有界力矩」的实现机制 |
| 数据流陈旧 → 零力矩 + `Fault` | **保留** | 安全 |
| `Fault` 状态与 `reset()` | **保留** | |
| `start()` 的包络交叉检查 | **保留** | 夹持力 vs `cont_torque_nm` |
| `stop()` 补 `disable()` | **保留**（本次已修） | 不修则每次退出必触发 T1 |
| `validate_config` 的速度/力矩耦合校验 | **重估** | `kd = grasp/speed` 的耦合消失后该规则失去依据 |

## 5. 状态 → 观测量

每帧从状态帧直接导出，不做状态机：

```
arrived  = |position_error| <= ε
holding  = |torque| >= k · torque_limit  且  |position_error| > ε
```

即「在使全力而且没到目标」。需要事件语义的调用方自己去抖——但**报告不需要去抖**，
这正是现在 `contact_samples` 在做而做不好的事。

`hold_position()`（爪实际停在哪）仍然有用，作为观测量保留。

## 6. 必须先测清楚的事

方案里有两处是推断，**不能直接当结论实施**：

### 6.1 夹持力默认值：定为 1.1 N·m（实测支持）

真实工件持续保持，24V，包络启用，绕组温度取自状态流：

| 夹持力 | 600 s 结果 | 温升速率演变 |
|---|---|---|
| **1.1 N·m** | 36 → **70 ℃** | 8 → 4 → 3 → 2 → **1** ℃/min |
| **0.6 N·m** | 41 → 49 ℃ | 末 60 秒 **0.00** ℃/min（已平） |

**1.1 的速率在持续衰减**，这是一阶趋近平台的特征而非线性爬升。拟合
`T∞ − T ∝ exp(−t/τ)`：**T∞ ≈ 75 ℃、τ ≈ 350 s**，低于固件 90 ℃ 温度墙约 15 ℃。
全程无故障、无欠压锁存、无链路中断，夹持位置零漂移。

**我先前判过一次「1.1 必然撞墙」，那是错的。** 依据是「432 秒时末段仍有
1 ℃/min」——但一阶系统接近平台时本来就还有残余斜率，而当时速率已经从 8 降到 1，
我只看了斜率的**值**，没看它的**趋势**。判「可无限期」要看速率是否在衰减，不是
看它是否归零。

保留项：两轮都从 36–41 ℃ 起测（前序余热），冷机平台会略低；高环境温度直接吃掉
那 15 ℃ 余量；要坐实平台需要 20–30 分钟长浸。

**`grasp_torque_nm` 不是硬上限**：实测反馈比预算高 4~7%（1.149 对 1.100，
0.643 对 0.600）。预算塑造命令，真正约束输出的是固件运动包络。

#### 这一轮里我犯的两个错，都记下来

**(1) 控制期间轮询 `read_status_ext()`。** `CONTROL_LAYERING.md` §1 明确写了
「控制期间无法轮询，ACK 会和控制帧对撞，实测 `read_status` 会超时」，我照样写进了
脚本，撑了 432 秒后输掉一次相位竞争，拿到 `TimeoutError`，并**把它误判成文档预测
的母线塌陷**。实际证据否定了那个判断：枚举时间戳全程未变（USB 没掉线重枚举）、
`latched_fault_code` 恒为 0（从未锁存欠压）。温度、状态位本来就在
`observation` 里，不需要任何额外命令。

**(2) 用 `observation.status` 套 `fault_code` 的判据。** 两者是不同字段：前者是
16 位 MIT 状态位，`Enabled=0x0001`、`Stalled=0x0004` 都**不是**故障——夹住东西按
定义就是堵转，把它当故障会让每一次成功夹持都被判成失败。正确掩码是 SDK 自己那份
（`has_serious_fault()`，0x0FFA）。

### 6.2 行进速度由什么决定

删掉速度阻尼后，速度由 `kp`/`kd` 与位置误差决定，全程移动起步会很快。可能需要
**轨迹斜坡**（按时间推进的位置设定点 + 抗积分饱和钳位）。

本次实施过一版斜坡并**失败了**：在 0.35 N·m 预算下误差窗口只有
`position_budget/kp = 0.00875 rad`，纹波一摆就撞钳位，位置项退化成恒力矩，而为腾预算
把 `kd` 砍半，结果纹波从 37% 涨到 50%、假阳性 0/10 变 3/5，已回退。

失败的根因是这条恒等式：

```
kp × error_limit = position_budget
```

**位置项的最大恢复力矩恒等于预算本身，与 `kp` 无关**；`kp` 只决定多快饱和。所以
0.35 N·m 的预算里换不来「阻尼 + 刚度」两全。

但在 1.0 N·m 预算下 `error_limit` 变成 0.05 rad，是摩擦滞后（0.005 rad）的 10 倍——
**斜坡结构在那个预算下可能成立**。这是推断，必须重测，不能因为它这次失败就否定结构，
也不能因为算式好看就当它成立。

## 9. 本次已落地、与本方案无关的修复

这两项已在真机验证，独立于重构：

1. **固件 build=20**：`s_mit_run_mode` 缓存改为**失能即失效**。原实现在 CAN 帧发送成功
   时就乐观更新缓存，而手册要求 run_mode 切换必须在停机状态下发送、否则电机忽略。
   一旦被忽略，缓存永久说谎，此后运动帧发给错误模式的电机被静默丢弃，而
   `target_seq`/`applied_seq` 正常推进、`last_error=0`、电机报 `mode=Motor` 且使能。
2. **SDK**：三个控制器 `stop()` 补 `motor().disable()`。此前每次控制器退出都把电机留在
   使能态，300ms 后必触发 T1 看门狗零速保持，进而改写运行模式。

修复前真机最多撑一两轮就卡死，修复后 10 轮开合全部正常。
