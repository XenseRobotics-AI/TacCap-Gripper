# 夹爪控制分层设计

> 固件与 SDK 的职责按**反应延迟**划分。安全包络放在丢一个包也不会失效的地方,
> 主机只负责意图。

硬件:EduLite05 / 9:1 / **24 V 供电**(电机额定 48 V)
固件:tc-gu-01 `feat/envelope-and-reachable-travel`(从爪 1.1.6,基于 1.1.5 `8f03cd2`)
证据:2026-08-27~28 在 `TCGU01A28Z0018s` / `TCGU01A25Z0012s` 上的实测

标注:**[实测]** 直接测到 · **[推算]** 由实测外推 · **[未验证]** 已实现但未在硬件上触发

---

## 1. 为什么包络必须在固件里

主机链路 100 Hz、相位锁,**且控制期间无法轮询**(ACK 会和控制帧对撞,实测
`read_status` 会超时)。主机侧保护的反应下限是几十毫秒,而 **8 rad/s 下 30 ms
就是 0.24 rad** —— 足够撞穿一个物体。

决定性证据是客户复现件 `gripper_loose_problem`:它用**裸 `submit_impedance()`**,
绕过 SDK 的全部保护。**但绕不过固件的 MIT 分支** —— 那是所有阻抗/位置/力/力位
混合命令的唯一必经点。

同一份代码、同一台设备、同一物体、`kp=20`,只切包络的一个标志位 **[实测]**:

| | 包络关闭 | 包络启用 |
|---|---|---|
| 结果 | **整机掉电重启**,USB 链路断开 | 25 秒稳定夹持 |
| 力矩 | 失控(索要 ~12 Nm,`0x700B` 削到 6) | 恒定 0.549 Nm |
| 状态 | `EN\|FAULT\|UNDER_VOLT`(客户)/ 链路丢失(我们) | `0x0001` 无故障 |

客户报告属实,且低估了严重程度:24 V 下 6 Nm 的电流需求不只拉垮电机,连 MCU
和 USB 桥一起拉垮。

## 2. 底层保护的真实边界

**电方向有底层兜底,热方向没有。** 这两句都要限定方向,不能泛化。

| 保护 | 状态 |
|---|---|
| 电机欠压保护 | ✅ **灵敏**,几秒内动作(客户案例 + 我们的复现) |
| 电机过温保护 | ❌ **到 100 °C 壳温都未动作** **[实测]** 297 秒恒 1.65 Nm,故障位全零 |
| 固件 MIT 路径堵转保护(1.1.5) | ❌ 无。`can_motor_gripper_stop_on_limit_stall()` 只挂在速度命令路径且只管行程末端 |

所以**热方向上,我们的温度墙是唯一防线**;电方向上不是。

## 3. 三层划分

**电机(内部环)** — 最终包络,谁都绕不过。`0x700B` 力矩、`0x7018` 电流、
`0x7028` CAN 超时(1.1.5 里只有 `#define`,从未写入)。

**固件(500 Hz)** — 安全包络 + 接触判定,权威层。每周期钳位;状态机;上报。

**SDK(100 Hz)** — 意图与标定。选模式、给设定值、归一化映射、可观测性。
**不实现自己来不及执行的安全逻辑。**

**控制器的力矩参数同样从设备读。** `ImpedanceConfig::for_spec()` /
`ForcePositionConfig::for_spec()` 拿 `Motor::get_spec()` 的规格推默认值:预算取
**连续堵转额定**、天花板取**旋转额定**、motion 上限取**力矩量程**。类里的成员
默认值是编译期烘进去的 EL05 数,换了电机就不对 —— RS00 上它把持续夹持限在
1.1 N·m,而那颗电机能无限期维持 3.6。

连带的一条必须一起动:**接近速度是 `预算/kd`**,所以 `kd` 也由预算推出
(`预算 / MOTOR_APPROACH_SPEED_RADPS`,目标 1.1 rad/s;EL05 得 kd = 1.0,RS00 约 3.27)。只提预算不提 kd,夹持力
上去了、接近速度也跟着上去 —— 那正是"把松放的物体撞飞而力矩从未升高"的那个区
(实测 5.5 rad/s)。`start()` 会拒掉推算出来超过 4 rad/s 的配置。

力矩的**边界**也不再是编译期常量:构造时只查结构和一个 20 N·m 的理智上限,
真正的界在 `start()` —— 那里能问设备,用它自报的额定卡。

包络的**数值**曾经也算在这一层("在固件允许范围内选"),现在不算了 —— 那是一次
分层错误。选不出正确的数:`cont` 的正确值是电机的连续堵转额定,而那个数电机自己
就报(`0x56` → `MotorSpec.stall_cont_torque_nm`),固件也按它钳。让主机侧"选"只是
多一处会选错的地方 —— 实测出的错就是 `--cont` 的默认值长期写着 1.6,而固件从来
按 1.1 执行。现在 SDK **读**这个数再写一次,`FollowerGripper::ensure_envelope()`,
调用方不提供任何数值。

## 4. 运动安全包络

`gripper_envelope_t` 覆盖在 `gripper_config_t.reserved[16]` 上 ——
**命令 `0x66/0x67`、载荷长度、结构体大小全部不变,串口协议零改动**。

```c
float    cont_torque_nm;       /* 可无限期维持 */
float    peak_torque_nm;       /* 运动瞬态 */
uint8_t  temp_derate_start_c;  /* 0 = 固件默认 90 */
uint8_t  temp_wall_c;          /* 0 = 固件默认 100 */
uint8_t  reserved0[4];
uint16_t flags;                /* 低位 VALID|ENFORCE,高 4 位布局版本 */
```

旧记录 `reserved` 全 0 → `flags=0` → 包络关闭,**升级不改变现有行为**。代价是
出厂设备上位置误差钳位、I²t、温度墙**一条都不执行** —— 90/100 的温度默认在
enforced 路径*内部*,不是兜底。

### 存的 ≠ 生效的

固件按型号把 `cont_torque_nm` 钳到 `motor_spec_active()->stall_cont_torque_nm`
(EL05 = 1.1),**钳位而不是拒绝**(拒绝会让 flash 里带旧配置的设备直接失去保护),
并且只打一条走物理 UART7 的限频日志 —— 主机侧看不到。而 `0x67` 读回的是 flash
里的记录,不是生效值。

所以"设了一个数、它一直显示着、却从来没生效过"是这个接口的默认体验:台架上的
`TCGU01A28Z0015s` 存着 `cont=1.800`、按 `1.100` 跑了几周。

`FollowerGripper::audit_envelope()` 把三者分开报:`stored`(flash 里的)、
`effective`(固件实际执行的,**为空表示它什么都不执行**)、`recommended`(按本机
电机规格推出来的)。控制器的启动检查比的是 `effective` —— 比 `stored` 会让一台
存着虚高 `cont` 的设备**消掉**本该响的那条警告。

**没有速度字段**,这是实测后删掉的:MIT 帧能钳的只有速度前馈,而阻抗走纯 PD
路径、该字段恒为 0;电机自己的 `limit_spd`(`0x7017`)是对的层,但 MIT 协议下
私有参数读写**电机不应答**(从爪固件 1.2.6 起会照常转发,结果是 `Timeout` 而不是
`InvalidParam`),切协议要断 24V 重启。**接近速度实际由 `peak/kd` 决定** ——
实测 `peak=1.5`、`kd=1.0` → 1.70 rad/s。

**没有命令超时字段**:MCU 侧定时器保护不了 MCU 自己挂住,`0x7028` 才是对的层。

## 5. 保护效果 [实测]

SDK 侧保护全部关闭,只靠固件包络:

| | 出厂 1.1.5 | 固件包络 |
|---|---|---|
| 峰值速度 | 8.68 rad/s | **1.70 rad/s** |
| 堵转力矩 | 应索要 5.72 Nm | **1.569 Nm** |
| **kp 不变性** | — | **kp 8→120(15×),力矩离散 1.4%** |

kp 不变性是最强的判据:不依赖任何绝对数值,也不受物体位置、标定方差影响。
`target_pos` 回报的是**钳位后**的目标,可在线比对判断包络是否生效。

## 6. 温度墙 [实测]

**平衡点稳定落在墙下方约 6 °C**,四档一致:

| 墙(起降/墙) | 平衡温度 | 平衡力矩 | 控制器 |
|---|---|---|---|
| 50 / 60 | 55~56 °C | 1.05 Nm | 裸阻抗 kp=20 |
| 60 / 70 | 64~65 °C | 1.28 Nm | 裸阻抗 kp=20 |
| 70 / 80 | 74.0 °C | 1.384 Nm(平 120 s) | 裸阻抗 kp=20 |
| **90 / 100(默认)** | **94 °C** | **1.370 Nm** | 力位混合力矩保持 |

**注意最后一行是不同控制器**,不能直接和上面三行比较握持力。
**裸阻抗在 100 墙下的平衡值未测到** **[未验证]** —— 7 分钟跑到 84 °C 仍在升,
尚未进入 90 °C 降额区。所以"100 比 80 对裸阻抗好多少"目前**没有依据**。

### 温度数据的三个陷阱

1. **厂商"工作温度 −20~50 °C"是环境温度规格,不是模组内部上限。** 曾据此得出
   几个错误结论。
2. **传感器读的是板/壳温,绕组更热且温差未知。** 按这类模组常见的 20~40 °C
   反推,94 °C 壳温对应绕组 114~134 °C,而 B 级绝缘额定 130 °C —— 坏假设下越界。
3. **绝缘老化累积、指数加速、且不报错。** 无法靠"测试没报错"证明安全。
   100 °C 墙是产品决定;基于实测的技术建议是 80。

## 7. 归一化位置 0.0

**从爪固件 1.2.5 之前,不是几何硬止点。** 自标定用*速度命令*顶到 `close_stall_torque_nm`(0.35 Nm)
堵转、后退 0.120 rad、回位、**带载设零** —— 预压烧进了零点定义。而 kd 形式的
MIT 帧发不出同样的推力(实测命令 0.359 Nm、反馈只有 0.213 Nm,≈0.59),
停在 0.0167 归一化、差 0.0202 rad。

当时固件把 `min_open_rad` 存成 0.020 内缩量,与开合端已有的
`OPEN_LIMIT_MARGIN_RAD`(0.029)对称。残差从 0.0167 降到 0.0089,**未完全解决**
**[实测]** —— 常数内缩本身不对,可达点和包络力矩耦合,正解是自标定末尾用当前
包络实测两端。

**从爪固件 1.2.5 起闭合端内缩已改为 0**(1.2.4 是 5 mrad),归一化 0.0 就是机械
硬止点,闭合端的压紧交给 `ForcePositionConfig::close_preload_nm` 的前馈力;SDK
因此拒绝打开低于 1.2.5 的从爪。本节上面的数据都早于这次改动。

另注:`max_open_rad` 四次开机自标定的极差达 0.109 rad(约 9% 行程)。根因是
`sanitize_confirm_count()` 直接丢弃参数恒返回 1,且采样路径只赋值不平均
(日志却写着 "average ... from N samples")。**按产品决定保持现状** —— 归一化
API 两端每次重测,方差被归一化吸收。

## 8. 三条踩过的坑

**布局错配。** 删掉一个 float 后 `sizeof` 仍是 16,字段整体错位 4 字节。SDK 写
新布局、固件读旧布局,而 SDK 读回来自洽 —— "读回来对、行为错",`peak=2.2` 实际
按 0.5 钳位,查了三轮。`static_assert(sizeof)` 的盲区正是**大小不变的布局变更**,
而这 16 字节是两个独立构建物之间的契约。→ `flags` 高 4 位加布局版本,固件不认
就拒绝执行。

**`reserved` 覆盖的代价。** 任何"从零拼配置再写入"的路径都会变成静默数据丢失。
已修两处(sanitize 转发、自标定 SAVE_MAX),但**每新增一个写入方都要记得带上
`reserved`**。更稳妥的做法是把读改写封装成唯一入口。

**热保护漏掉纯力矩路径。** `effective_peak()` 只在 `clamp_target()` 里被调用,
而它在 `kp<=0` 时直接返回 —— 力位混合的力矩保持正是 `kp=kd=0`。修复时又发现
温度墙被放在依赖 `dt` 的提前返回下游,同毫秒的第二次调用会整条跳过。
**结构错误**:I²t 需要 `dt`,温度墙不需要任何历史、必须无条件生效。

## 9. 状态流里的重复帧(机制确认,量级未定)

**代码事实**:数据流任务按**自己的定时器**推送 `can_motor_get_cached_status()`
的缓存值,**不检查这份数据是不是新的**(`task_data_stream.c`)。电机的主动上报
也是 100 Hz(`epscan=1`,已是上限)。两个独立时钟意味着**结构上必然可能**出现
同一份数据被推两次。这一条是读代码得出的,可靠。

**量级则不可靠。** 两次测量差了一个数量级:

| 场景 | 重复位置帧 |
|---|---|
| 阶跃到全闭,2 秒窗口(含起步加速段) | 42% |
| 4 s 周期正弦,24 秒,`kp=8` | 4% |
| 同上,`kp=20` | 2% |

第一次那 42% 里很可能有相当一部分来自**起步瞬间位置几乎不动**,而不是拍频 ——
2 秒窗口里起步占比很大,采样偏了。**我据此把顿挫归因于拍频,证据不足。**

两次测量都确认的是:**帧间隔本身很稳**(中位 9.53 ms、max 11.65 ms),
`submit_hz` 100.0~100.3,**主机侧一帧不丢** —— UART 那一跳的按状态帧相位提交
在正常工作,问题(如果有)在它的上游。

**顿挫的成因目前没有定论。** 正弦轨迹实测跟踪误差稳定(`kp=20` 时中位
0.029~0.033、max 0.047),看不出顿挫。要复现需要知道当时是阶跃还是连续轨迹 ——
阶跃时误差钳位会介入(窗口 `peak/kp`),那是另一套动力学。

若要消除重复帧,改法是让 MCU 的推送由**收到电机帧这个事件**驱动而不是自己的
定时器 —— 和主机侧控制器按状态帧相位提交同一思路,只是在电机→MCU 这一跳
再做一次。**按产品决定暂不改动。**

## 10. 未验证清单

  触发过的记录**
